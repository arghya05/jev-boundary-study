Agent Foundry: A Boundary-Preserving Architecture
for Governed Agentic Platforms

Abstract
Agent frameworks expose tools, delegation, memory and human approval, yet
the controls attached to a request (identity, tenant, scopes, budgets, deadlines,
rate limits, fail behavior) are routinely lost at execution boundaries: delegation,
threads, streaming, resume, caching, retrieval and adapter exports. We present
Agent Foundry, an open-source Python platform whose architecture is organized
around one principle: every control is a property of the request’s execution scope,
not an argument that each layer must remember to pass . We formalize this as the
Governed Execution Contract (GEC), a meet-semilattice of control scopes with
seven invariants, and prove that delegation can only attenuate authority, that deny
rules can only tighten resolution, that per-principal rate limits are exact under arbi-
trary thread interleavings, that every call yields exactly one audited decision even
when the policy source is unreachable, and that admission partitions by principal
without cross-shard coordination. On AgentGovBench, a public 48-scenario gov-
ernance benchmark, Agent Foundry passes 48/48 in 10 of 10 repetitions, against
46/48 for the best published governed conﬁguration and 13/48 for each of 7 pub-
lished framework-native runners; run through the same harness, Microsoft’s Agent
Governance Toolkit scores at most 46/48 and Bounded Agents 36/48, and on a
24-scenario suite authored blind to our code Agent Foundry scores 24/24 against
17 and 8. A set of 13 single-control ablations attributes 35 of the 48 scenarios
to speciﬁc mechanisms and exposes a measurement problem: a runner that denies
every call scores 31/48, above the audit-only reference, and two controls can be re-
moved without losing an ofﬁcial point. Eight supplemental discriminating scenar-
ios and three anti-vacuity checks close that gap. A 360-degree evaluation covers
the remaining layers: multi-agent coordination overhead is 5.6–154 × lower than
LangGraph’s on identical topologies; the control plane adds 14 µs per call over
the tool gateway and scales to 25,172 governed calls/s across 8 principal-afﬁne
shards with exact limits; budgeted context assembly retains a planted fact in 100%
of cases up to 1,426,941 history tokens where a recency window retains 20%; a
trained input gate raises held-out prompt-injection recall from 0.0% to 80.0%. On
WorkBench, matched Foundry runtimes are statistically indistinguishable from
the benchmark’s reference loop with one model; we do not claim task-level state
of the art. All results regenerate from committed raw evidence.
1 Introduction
An agentic platform turns one user request into many executions. An orchestrator delegates to
specialists; specialists fan out to workers on threads; a run pauses for approval and resumes in
another process; a cache answers a repeated prompt; a retriever injects documents into context; a
tool is exported to a different framework. The request, however, arrived with controls attached: who

the caller is, which tenant owns the data, which scopes were granted, how much may be spent, how
many calls per minute are allowed, and what to do if the policy service is down. Each boundary
above is a place where those controls can silently disappear.
This is not hypothetical. In a source review of Agent Foundry before this work, request deadlines,
cancellation and deny-all tool policies were ignored at the public API in both of its runtimes; a
viewer’s request routed through a native supervisor executed an admin-only tool while the Lang-
Graph runtime correctly denied it; a human approval overrode an external policy engine that was
never consulted; and a prompt cache ignored tool schemas (§ 6.4). Public evidence shows the same
failure class across the ecosystem: on AgentGovBench [ 1], each of seven widely used frameworks
and coding agents scores 13/48 when run without an external governance layer: as run, none propa-
gates the end user’s identity into an audit record, narrows delegated scope, or aggregates rate limits
across subagents.
We argue that these are not independent bugs but consequences of an architectural choice. Many
frameworks treat controls as arguments: values that each layer must receive and forward. Every
new boundary is then a new opportunity to forget one. Agent Foundry instead treats controls as
a property of the execution scope of a request. Scopes compose by a meet operation, so nesting
can only narrow them; live handles (budgets, cancellation tokens) are kept out of persisted state;
and a single deny-ﬁrst admission point decides and audits every tool call. We call the resulting
speciﬁcation the Governed Execution Contract (GEC).
Research questions. RQ1 (foundations): can the control semantics an enterprise platform needs
be stated as a small algebra whose laws are provable and machine-checkable? RQ2 (governance):
does a boundary-preserving architecture meet a public governance benchmark, and which mecha-
nisms are responsible for which outcomes? RQ3 (measurement): do existing governance bench-
marks distinguish correct enforcement from trivial behavior? RQ4 (cost and breadth): what do
the controls cost, and how does the platform perform on the other layers—orchestration, context,
security ﬁlters, evaluation, task execution and scale?
Contributions.
1. A formal contract. The GEC (§ 3) models control scopes as a meet-semilattice and
states seven invariants. We prove attenuation along arbitrary delegation chains, deny-
monotonicity of policy resolution, exactness of per-principal rate limits under arbitrary
interleavings, decision totality under policy-source failure (including an impossibility argu-
ment for reading the fail mode from the failed source), and coordination-free sharding by
principal. Property-based tests check the algebraic laws on randomly generated policies
and chains.
2. A platform architecture. Agent Foundry (§ 4) realizes the contract across seven layers:
declarative entry points, a think–act–critique orchestration loop, a runtime seam with a
native engine and a LangGraph engine, a governed tool gateway, a multi-tenant control
plane, an LLM gateway, and a budgeted context layer, with evaluation and observability as
cross-cutting rails. We describe the design decisions that differ from common practice and
why.
3. State-of-the-art governance results with mechanism attribution. Agent Foundry passes
48/48 AgentGovBench scenarios in 10/10 repetitions, above every published conﬁguration
(best 46/48) and above the two closest open-source systems run under our harness (Agent
Governance Toolkit at most 46, Bounded Agents 36); on 24 scenarios written blind to our
code it scores 24/24 against 17 and 8. Single-control ablations (13) attribute 35 scenarios
to speciﬁc mechanisms (§ 6.1).
4. A measurement ﬁnding and remedy. Extending trivial-agent sanity checks [ 77] to an en-
forcement benchmark: Constant policies pass most individual scenarios (44/48 are passed
by at least one trivial runner); a deny-everything runner scores 31/48; and 2 controls (dele-
gation attenuation, deny-overrides resolution) can be removed without losing a point. Pub-
lished runs corroborate this: 6 of 8 governed runs pass the task-narrowing scenario while
declaring that they do not implement task narrowing. We contribute eight discriminating
scenarios and three anti-vacuity checks (§ 6.2).

2 Related Work and Research Position
We compared Agent Foundry with about forty systems and papers; Table 1 summarizes the closest,

Agent architectures and frameworks. ReAct [ 73], Reﬂexion [ 57] and Self-Reﬁne [ 40] estab-
lished the reason–act and self-critique loops that our think–act–critique cycle follows; CoALA [ 61]
supplies the memory/action/decision vocabulary our layers map onto. AutoGen [ 68], MetaGPT [ 24],
CAMEL [ 34] and multi-agent debate [ 20] motivate our six topologies, and MAST [ 7] catalogues
their failures. None of these is our contribution. Production frameworks provide the mechanisms
of pause, resume and approval: LangGraph [ 33] persists interrupts and implements cooperative
timeouts; Pydantic AI [ 53] wraps approval-required toolsets and declares per-engine durability;
CrewAI [ 12] persists ﬂows but drops callable guardrails on serialization; Microsoft Agent Frame-
work [ 46] matches approval rules to tools and arguments; Deep Agents [ 32], the OpenAI Agents
SDK [51] and Google ADK [ 21] offer subagents, guardrails and plugins. Their own documentation
or code shows the boundary problem this paper addresses: subagent budgets and rate buckets are
per agent rather than per principal (ADK’s agent tool, Microsoft Agent Framework’s budget keys);
Deep Agents’ subagent permissions replace the parent’s and default to allow; and approval takes
precedence over conﬂicting sticky decisions in the OpenAI SDK. Their AgentGovBench native
rows are 13/48.
Delegation and authorization for agents. Multi-hop attenuation by intersection is established.
Bounded Agents [ 49] attenuates scope along a principal chain and adds composition closure, dele-
gation budgets, single-use hash-bound approvals and intent binding, reducing AgentDojo exﬁltration
to zero at a utility cost of 8.6–13.9 points. Bounded Agents also states cumulative consumption as an
invariant—each child inherits its parent’s consumed budget as a ﬂoor [ 49]—and CapLease charges
a delegated child against its parent’s authorization budget [ 70]; these are our I4 for a single chain
or a single authorization, and our addition is keying shared buckets by principal and tenant across
sibling threads with exact windows under concurrency (Theorem 3). Further, CAPMAS [ 64] and
Overlaying Governance [ 25] formalize capability and compositional delegation; Delegation With-
out Trust [ 14] ﬁnds LangGraph, CrewAI and AutoGen exposed to confused-deputy and escalation
threats and proposes a token broker; MiniScope [ 76], SEAgent [ 28], authenticated delegation [ 59]
and ScopeGate [ 42] treat least privilege, mandatory access control, OAuth-style delegation and the
gap between exposing a tool and authorizing it. Forbid-ﬁrst combination is also established: Pro-
gent [ 56] evaluates forbid rules before allow rules with a default block, and ActGov [ 75] and the
Agent Governance Toolkit [ 45] use deny-overrides. Per-principal budgets across agents exist for

Content and information-ﬂow security. CaMeL [15] and FIDES [ 11] track information ﬂow and
attach capabilities to data, defending against prompt injection by construction; the design-patterns
paper [ 6] argues for such architectural defenses. These are strictly stronger than our ﬁlter-based I6.
Classiﬁer and rail systems—NeMo Guardrails [ 54], Guardrails AI [ 22], Llama Guard [ 26], Prompt
Guard [ 43], Invariant [ 27]—and policy or veriﬁer approaches—AgentSpec [ 65], AgenTRIM [ 5],
SABER [ 13], ProbGuard [ 66], Conseca [ 63], ShieldAgent [ 9], GuardAgent [ 69], DRIFT [ 35]—
decide whether content or an action is acceptable. The GEC is orthogonal to all of them: it guaran-
tees that whichever policy or detector is used is evaluated with the right principal, tenant, attenuated
scope, shared budget and fail behavior at every boundary.
Governance products and audit. The Agentic Control Plane gateway [ 2] is the closest compara-
tor for our control plane and supplies the strongest published AgentGovBench runs. Microsoft’s
Agent Governance Toolkit [ 45] binds approvals to action digests, policy versions and expiry, con-

3 The Governed Execution Contract
This section states the contract that the architecture implements. The deﬁnitions follow the code
closely (module and symbol names are given), so that each theorem is a statement about the shipped
system rather than an idealization; assumptions that the code does not discharge are stated explicitly.

3.3 Deny-ﬁrst admission
Admission ( ControlPlane.invoke) evaluates, in order: (1) authentication ( u ̸= ε); (2) policy-
source availability; (3) tenant existence and membership u ∈ members(τ); (4) tool registration; (5)
resolution r = res( u, x, t) ̸= ⊥; (6) required scopes req(x) ⊆ eﬀ; (7) r.p ̸= deny; (8) the rate
limit; then execution through the governed gateway, which re-checks allowlist, scopes, budget and
approval (GovernedToolGateway). The ﬁrst failing check determines the reason.
Proposition 1 (Totality and one decision per call) . Every invocation terminates with exactly one
decision in {allow, ﬂag, deny} and appends exactly one governance_decision audit record, in-
cluding when the policy source raises, when the gateway denies, and when the tool fails.
Proof. Each branch of invoke and _execute returns the value of _record, which appends one
record and constructs the decision. PolicySourceUnavailable is caught at step (2); in _execute,
PermissionDenied and every other exception raised by the gateway (budget exhaustion, cancella-
tion, deadline, unexpected errors) are converted into a recorded denial; a tool that fails after admis-
sion yields an allowed decision with a failed result. No other path returns. The argument assumes
that the audit sink itself does not raise.
Proposition 2 (The fail mode must be local) . Let the decision under an unavailable policy source
depend on a tenant-conﬁgured fail mode fτ ∈ { open, closed}. If fτ is stored only in the policy
source, then for a tenant whose ﬁrst request arrives during an outage, no admission procedure can
honor fτ = open.
Proof. During the outage the procedure’s inputs are the request and local state. If fτ is stored only
remotely and has never been read, local state is identical for fτ = open and fτ = closed, so the
procedure returns the same decision in both worlds; it must deny for closed, hence cannot allow for
open.
The ﬁrst version of our control plane learned fτ from successful reads and failed AgentGovBench
scenario fail_mode_discipline.02 for exactly this reason; the shipped version takes fτ as de-
ployment conﬁguration and refreshes it on reads (ablation “locally declared fail mode” in Table 5).
3.4 Rate limits under concurrency
Let calls for key κ = ( τ, u, t) be admitted by SlidingWindowLimiter.try_acquire, which
under a mutex drops timestamps older than W and admits iff fewer than ℓ remain.
Theorem 3 (Exactness under arbitrary interleavings) . Assume a monotone clock and that each call’s
check-and-append executes under the mutex. For any ﬁnite set of concurrent calls on key κ and any
interleaving: (safety) every interval of length W contains at most ℓ admissions; (liveness) if n calls
reach the limiter within one window and no earlier admission for κ lies in that window, exactly
min(n, ℓ) are admitted. Calls denied at steps (1)–(7) do not consume capacity.
Proof. Because each check-and-append is atomic, the execution is equivalent to a sequential history
ordered by lock acquisition (linearizability of a critical section). In that history, the deque for κ
contains exactly the admissions within the trailing window at each step, and an admission occurs iff
its size is below ℓ; so the count in any window never exceeds ℓ (safety), and the ﬁrst min(n, ℓ) calls
in lock order are admitted while the rest see a full deque (liveness). Steps (1)–(7) precede the limiter
and return before try_acquire.
One consequence is worth stating: a call that passes the limiter but is then denied by the gateway (for
example by a second-line scope check or an exhausted step budget) has consumed capacity. Checks
that can deny should therefore precede the limiter, which is why the plane re-implements the scope
check the gateway also performs. The assumption of a monotone clock matters. The ﬁrst campaign
used wall-clock time for windows and recorded one repetition, out of 6 ×3, in which a principal was
not admitted exactly ℓ times; the anomaly did not reproduce in 30 reruns. A wall-clock adjustment
can shift a window, so the shipped limiter uses time.monotonic; all 10 repetitions at every thread
count in the later campaigns are exact (§ 6.5).

3.5 Partitioned admission
Proposition 3 (Coordination-free sharding) . All mutable admission state (limiter deques, learned
fail modes) is keyed by (τ, u, t) or τ, and policy documents are read-only per call. If requests are
routed by a function of (τ, u), then K independent control planes, each holding the policy of its
principals, produce the same decisions as one control plane, with no messages between shards;
aggregate throughput is bounded above by K times single-shard throughput.
Proof. A decision for (τ, u, t, x) reads the policy of τ, the membership and scopes of u, and the
deque for (τ, u, t), and writes only that deque and one audit record. Routing by (τ, u) places all
reads and writes for a key on one shard, so each shard’s execution is a restriction of the single-plane
execution to its keys, and the union of the restrictions equals the whole.
Principal-afﬁne routing is a deployment pattern, not a library component:
benchmarks/sharded_scaling.py implements the router used in § 6.5. Budget buckets
shared across principals (for example a tenant-wide cost ceiling) are the exception to the proposi-
tion: they need a shared counter, which the RunBudgetLike protocol permits but which we do not
evaluate. Each bucket’s charge is atomic under its own lock, but a charge applied to several ancestor
buckets is not one transaction; MasuGate [ 52] addresses budget consistency under concurrent
effects.
3.6 The seven invariants
Collecting the above, the GEC requires: I1 attenuation (Thm. 1); I2 deny precedence—hard denials
precede approval requests in the PDP, and resolution is deny-monotone (Thm. 2); I3 live/persisted
separation—budget and cancellation handles are never serialized, and resume re-derives controls
from the current request; I4 shared accounting across children (Thm. 1, budget clause; Thm. 3); I5
complete cache identity—a prompt-cache key digests the full effective request, including tools, call
identiﬁers, sampling options and response format, and the calling tenant and user from the scope; I6
a uniform content boundary—user input, retrieved passages and tool results pass the same injection
detectors (retrieved passages ﬂagged by them are dropped and PII-redacted; ﬂagged tool results are
labelled untrusted rather than dropped, because they are often the data the caller asked for); and
I7 measurement honesty—a missing oracle is unmeasured rather than passed, an empty gate fails,
and failed or interrupted attempts remain in denominators with their costs. I3, I5, I6 and I7 are
implementation obligations checked by regression suites (§ 6.4) rather than theorems.
3.7 Measuring whether a benchmark measures
Let B be a benchmark of scenarios s with pass predicate pass(s, o) over observed outcomes o. Let
R0 be a set of trivial runners : constant or enforcement-free policies (no governance, audit-only,
deny-everything, allow-and-audit).
Deﬁnition 3. Scenario s is vacuous if ∃r ∈ R 0 with pass(s, or). Given a system F and single-
control ablations F−c, s is attributed to c if pass(s, oF )∧¬pass(s, oF−c ). A control c is unobservable
in B if no scenario is attributed to it.
A benchmark score is informative about a mechanism only through scenarios attributed to it; an
unobservable control can be deleted without changing the score. We complement pass predicates
with three anti-vacuity checks computed on outcomes: decision coverage (one audited decision per
attempted call), effect ﬁdelity (executed effects equal allowed outcomes) and liveness (a scenario
that expects any allowed or rate-limited call admits at least one call).

scoped_execution, which converts an ExecutionContext into the request scope of § 3. This
is where controls enter; lower layers read them from the scope rather than from parameters (direct
graph-state callers retain an older state-key interface, which the resolvers also honor).
L1 Orchestration. A turn runs think (prompt assembly and a model call), act (tool calls, dis-

L2 Runtime seam. Execution is a WorkflowEngine protocol ( build, run, stream, resume)
selected from a registry. Two engines implement it: a from-scratch native loop, and a LangGraph
StateGraph engine for LangGraph’s checkpointing and interrupts. The same conﬁguration runs
on either, which enables the differential testing of § 6.4. Native single-agent state persists through
versioned StateStores (in-memory, SQLite, Redis, Postgres) with optimistic version checks.
L3 Tool effects. The control plane (control_plane.ControlPlane) is the multi-tenant ad-
mission point of § 3: tenant policy documents re-read per call, tier-aware rules with deny-
overrides, per-principal sliding-window limits, attenuating delegation, a locally declared fail mode,
and one audit record per decision. Admitted calls execute through the governed tool gateway
(GovernedToolGateway), which requires a trusted user and tenant on every call, re-applies the
policy decision point (allowlist, declared scopes, data classiﬁcation, optional OPA or Cedar engine,
egress allowlist, approval), enforces budgets and JSON-Schema validation of inputs and outputs,
binds idempotency keys to principal and payload, and audits admission and results. MCP servers’
tools enter as ordinary tool speciﬁcations and are governed identically.

4.2 Design decisions and their origin
We state which ideas are borrowed and which choices are, to our knowledge, speciﬁc to this design;
§2 compares them with the closest systems.
Controls as scope, not arguments. Capability systems [ 19, 47] and the principle of least privi-
lege [ 55] are old; the confused-deputy problem [ 23] is exactly the delegated-identity failure we ob-
served. Our contribution is to apply them at every agent execution boundary —sync, async, stream-
ing generators, resume, threads, fan-out, DAG, batch, adapter exports—through one context-variable
scope with a meet operation, so that adding a new boundary requires wrapping it, not threading a
new argument through each layer. Streaming generators re-enter the scope at every step so that a
consumer’s own context is restored between yields.
Live handles are not state. Checkpointing frameworks persist graph state; if a budget object or
cancellation token is persisted, resume either loses it or resurrects a stale one. We keep them out of
checkpoints and require callers to re-supply controls on resume, so a revoked role takes effect on the
resumed run. This trades convenience (controls must be supplied again) for the property that per-
sisted state can never widen authority. It also has a cost that CapLease [ 70] and ResidualAuth [ 10]
make precise: state that must narrow authority across resume, such as a consumed single-use ap-
proval or a revocation history, cannot be re-derived from the request and needs a durable, monotone
store. Agent Foundry does not yet provide one; its approvals are re-checked on resume against
current policy but are not single-use.
Deny-ﬁrst, single admission. A decision pipeline that checks approval before hard policy lets
approval override policy; we observed this in the original code. The PDP and the control plane
evaluate unconditional denials before approval requests, and rate limiting is evaluated last so that
denied calls do not consume capacity (Thm. 3).
Fail mode is deployment conﬁguration. Proposition 2 shows that a fail mode stored only in the
policy source cannot be honored for a tenant ﬁrst seen during an outage. We found this empirically
before proving it.
Unmeasured is not passed. Evaluation harnesses often default a missing oracle to success or
drop failing cases. Agent Foundry’s gate distinguishes failed, unmeasured and passed, and our
benchmark harnesses keep runner exceptions and interrupted attempts in ﬁxed denominators. The
same principle motivates the anti-vacuity checks of § 3.7. DEMM-Bench applies the same rule to
benchmark reporting, recording unexercised axes as not evaluated rather than as passes [ 58].
Engine neutrality as a test oracle. Supporting two engines is common. We use the second engine
as a differential oracle: identical scenarios run against both, and any divergence in control outcomes

6.2 Do governance benchmarks measure enforcement?
Three observations answer RQ3. First, constant policies score well: a runner that denies every
call and audits the denial scores 31/48, above the audit-only reference (29), and an allow-and-audit
runner scores 25. Individually, 44 of the 48 scenarios are passed by at least one trivial runner;
only 4 require both an allowed and a denied outcome. Aggregate scores still separate systems, but
most single scenarios cannot distinguish enforcement from a constant. Second, two controls are
unobservable: without attenuation, Agent Foundry still scores 48/48, because the only narrowing
scenario (scope_inheritance.04) conﬁgures no subagent-tier rule, so a fail-closed default denies
the call before narrowing matters; without deny-overrides it also scores 48/48, because no scenario
contains conﬂicting incomparable rules. Third, published results show the same gap independently:
6 of the 8 published governed runs that declare “does not currently enforce task-scoped narrowing”
nevertheless pass scope_inheritance.04.
Remedy. We wrote eight supplemental scenarios in the upstream format, each designed so that a
speciﬁc control is necessary: narrowing with an allowed subagent tier; multi-hop narrowing where
a grandchild re-requests a dropped scope; a user-wide allow against a tool-wide deny; one user ID
in two tenants with different scopes; revocation affecting only its tier; concurrent rate limiting that
must admit as well as deny; background-tier denial; and ﬂagging. They are listed in Appendix A.
Agent Foundry passes 8/8; vanilla, audit-only, deny-everything and allow-and-audit pass 0, 0, 0 and

Long context. We plant one fact at ﬁve depths in threads of 100 to 50,000 turns (2,865, 28,381,
285,415, 1,426,941 tokens) with three seeds, and require each strategy to produce context within a
2,000-token budget (Table 9). A recency window, the common default, keeps the fact only when it is
recent (20% at the largest size); passing the full history keeps it but exceeds the budget by up to 732 ×.
Foundry’s budgeted pipeline retains the fact in 100% of cells at every size with about 231 tokens of
context, assembling 1,426,941 tokens of history in 68 ms. The default lexical retriever fails when
the query is paraphrased (0%); swapping in the embedding store behind the same protocol restores
retention to at least 87% at the sizes we could index (6.2 s to index 1,000 turns). With 20 planted
injection passages that share the query’s keywords, the recency window admitted 5 into context
across 6 runs and the Foundry pipeline admitted 0, while still returning the fact. This benchmark
measures context assembly; whether a model then uses the fact is a separate question.

7 Discussion
What any agent framework should adopt. The results suggest a short checklist that is indepen-
dent of Agent Foundry’s code. (1) Establish controls once, at entry, as an execution scope that every
boundary—threads, generators, resume, fan-out, exports—re-enters, and compose nested scopes by
a meet. (2) Never persist live handles; re-derive controls on resume. (3) Decide every effect at one
deny-ﬁrst admission point, and evaluate rate limits last so denials do not consume capacity. (4) Key
limits by principal, not by agent or thread, so that fan-out cannot multiply a quota, and shard by that
key. (5) Make the fail mode local conﬁguration (Proposition 2). (6) Emit exactly one audit record
per decision, including denials and outages. (7) Treat unmeasured as distinct from passed, and report
governance scores together with ablations or trivial-runner baselines; a score that a deny-everything
runner nearly matches says little by itself.
Why governance, and not task accuracy, is where the architecture shows. Task benchmarks
such as WorkBench are dominated by the model: published full-set runs range from 406 of 690 for
the model we used to 674 of 690 for the strongest, a spread that dwarfs the differences among our
arms. A governed platform’s value is that controls hold when the model, the topology or the de-
ployment changes, which is exactly what task accuracy does not measure. Conversely, governance
18

PAGE 19
benchmarks are cheap to run and deterministic, which makes them easy to overﬁt; mechanism attri-
bution and discriminating scenarios are the counterweight.
7.1 Threats to validity
Benchmark-driven development. The control plane was written during this study, after reading
AgentGovBench’s scenarios. A system built to a test suite can pass it without generalizing. We
mitigate this in three ways, none of which removes the threat: every allow/deny decision is made by
library code that has its own unit and property tests independent of the benchmark; ablations show
that each passing category depends on a mechanism rather than on scenario-speciﬁc logic; and eight
supplemental scenarios probe behavior the ofﬁcial suite does not. The supplemental scenarios are
ours; the blind suite (§ 6.3) was written without access to our code, but by an AI author from the
same model family, so a suite written by independent humans would be stronger still.
Harness choices. The virtual clock and threaded fan-out differ from the upstream runners, and
both are disclosed. Threaded fan-out is stricter. The virtual clock matters only for the one recovery
scenario, where the upstream reference runner sleeps through the same outage.
Comparators. Published AgentGovBench rows were produced by their authors against a live gate-
way, not rerun by us; their declared-unsupported scenarios are counted as published. The runners for
the Agent Governance Toolkit and Bounded Agents were written by us; a mapping by their authors
might score higher, and we report the most favourable of the two toolkit conﬁgurations we tried.
The trivial runners are ours.
Scope of the non-governance benchmarks. The long-context benchmark is synthetic and mea-
sures assembly, not use by a model; the injection data set is small (116 test prompts) and partly
non-English; HaluEval-QA has the length artifact we document; the scaling results are from one
machine; and the WorkBench study uses one model, one repetition and subsets of 12 and 60 tasks.
7.2 Limitations
We did not measure the utility cost of attenuation, which MasDrift [ 71] and Bounded Agents [ 49]
show can be substantial; AgentGovBench has no model and therefore cannot. The audit log is
not tamper-evident, approvals are not bound to action digests or consumed once, and there is no
information-ﬂow tracking; the Agent Governance Toolkit, Bounded Agents and CaMeL/FIDES are
ahead on each. Process-local scopes are not an isolation boundary against malicious Python tools;
the platform’s in-process sandbox is for trusted code only. Cooperative cancellation does not stop a
tool already running. Distributed budgets, fenced ownership of shared state, durable reconciliation
of external effects (no exactly-once guarantee), authenticated approval resume for exported tools,
and opaque CrewAI internals remain open, as does multi-agent planning quality, which we did not
evaluate. AgentDojo, τ2-bench and MultiAgentBench require model-driven runs that we did not
perform. The trained injection gate is a lexical model and should be replaced by or combined with a
model-based detector where available.
Broader impact. Explicit, testable controls can make it safer for small teams to deploy agents
that take actions. The same results could be over-read: a perfect governance score does not certify
a deployment, and ﬁlters do not make untrusted content safe. We report the conditions under which
each result holds and the mechanisms it depends on, so that readers can judge transfer to their setting.
8 Conclusion
Controls attached to a request must survive every boundary a platform creates, and the way to make
them survive is architectural: represent them as a composable execution scope and decide every
effect at one deny-ﬁrst admission point. We formalized this as the Governed Execution Contract,
proved its central properties, implemented it in Agent Foundry, and showed a perfect, repeatable
AgentGovBench score whose passing scenarios are attributed to speciﬁc mechanisms. The same
analysis shows that governance benchmarks need ablations, trivial baselines and discriminating sce-
narios before their scores can be read as evidence of enforcement, and we supply those. Across

B Ablation deﬁnitions
Ablations patch runner-owned objects after setup ( benchmarks/agentgovbench/ablations.
py); the production control plane has no ablation ﬂags. Delegation attenuation : delegated scopes
ignored. Delegation chain : chain omitted from audit. Principal rate limiter : limiter always ad-
mits. Locally declared fail mode : fail mode learned only from successful reads (the original design).
Honor fail-closed : outages always fail open. Tenant membership: a principal known in any tenant
is accepted in every tenant. Deny-overrides: the ﬁrst deﬁned rule in the order user–tool, user, tool,
default wins. Per-call policy read : a policy snapshot from setup is used. Decision audit : no audit
records. Plane scope check : the control plane’s required-scope check is removed while the gateway
PDP keeps its own. All scope checks : both removed. Tier rules: every tier resolves to allow. Anony-
mous principal : an empty uid is replaced by a member principal. The two probes, deny-everything
and allow-and-audit, bypass enforcement entirely but still write audit records through the plane’s
recorder.
C Anti-vacuity checks
For each ofﬁcial scenario the harness records the number of attempted calls, audited decisions, al-
lowed calls and, for runners that expose them, executed tool effects. Decision coverage holds if
attempts > 0 and decisions = attempts. Effect ﬁdelity holds if executed effects = allowed calls,
so an allowed decision that never ran the tool, or an effect without an allowed decision, is detected.
Liveness applies to scenarios whose expectations include tool_allowed or rate_limited_count
and holds if at least one call was admitted; it rejects a deny-everything system on exactly the scenar-
ios whose upper-bound assertions it otherwise passes. These checks are reported beside, not inside,
the ofﬁcial score.

E Scenario-level vacuity
Of the 48 ofﬁcial scenarios, 44 are passed by at least one of the four trivial runners (no governance,
audit-only, deny-everything, allow-and-audit) and 4 by none. The non-vacuous scenarios are those
that require an allowed and a denied outcome for different principals, tools or times within one sce-
nario (for example, a user override that allows one principal while denying another). A benchmark
that wants per-scenario diagnostic value, rather than only an aggregate, beneﬁts from pairing each
deny expectation with an allow expectation that a constant policy cannot satisfy.
